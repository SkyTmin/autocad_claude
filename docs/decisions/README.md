# Architecture Decision Records (ADR)

Здесь живут решения, которые формируют проект и должны быть прослеживаемыми.

## Когда писать ADR

См. `docs/workflow.md` → *"Когда писать ADR"*.

## Формат имени

`NNNN-краткое-имя.md`, где `NNNN` — 4-значный порядковый номер, `краткое-имя` —
2–4 слова через дефис.

Примеры: `0001-hybrid-autolisp-dotnet.md`, `0002-spec-driven-development.md`.

## Структура файла

```markdown
# ADR-NNNN: <заголовок>

**Статус**: Принято | Заменён ADR-XXXX | Отменён
**Дата**: YYYY-MM-DD

## Контекст
Что происходит, какая проблема, какие вводные.

## Решение
Что мы выбрали, явно и однозначно.

## Альтернативы
1. **<альтернатива A>** — почему не выбрали.
2. **<альтернатива B>** — почему не выбрали.

## Последствия
- Положительные:
- Отрицательные / риски:
- Отзывность: <легко/сложно/невозможно отменить>

## Критерии пересмотра
Когда стоит пересмотреть это решение.
```

## Как менять решение

ADR **не правится**. Создаётся **новый** ADR, который:
1. Ссылается на старый (`Заменяет ADR-XXXX`)
2. Описывает новый контекст (что изменилось)
3. Описывает новое решение

В старом ADR обновляется только поле "Статус" → `Заменён ADR-YYYY`.
