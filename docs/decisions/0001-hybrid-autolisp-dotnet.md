# ADR-0001: Гибридная архитектура AutoLISP + Python/.NET

**Статус**: Принято
**Дата**: 2026-05-03

## Контекст

Шамиль — геодезист-камеральщик в Civil 3D. Задачи делятся на два класса:

1. **Внутри Civil 3D** — построение, импорт точек, генерация подписей,
   работа с COGO Point, поверхностями, трассами. Нужен прямой доступ к API
   AutoCAD/Civil 3D, ввод/вывод через командную строку CAD.

2. **Подготовка/обработка данных снаружи** — Excel→CSV, batch-обработка
   множества файлов, потенциальный UI отдельным окном, интеграция с
   приборными выгрузками (txt, sdr).

Один инструмент плохо покрывает обе зоны.

## Решение

Гибридная архитектура:

- **AutoLISP** — основной язык для команд внутри Civil 3D.
  - Прямой доступ к ActiveX API AutoCAD и Civil 3D objects
  - Быстрая итерация (загрузка через `APPLOAD` без компиляции)
  - Бесплатно, без Visual Studio
  - Огромная база готовых решений для съёмки (Lee Mac, esurveying.net)

- **Python** — внешний слой для всего, что выходит за рамки CAD:
  - Парсинг Excel/CSV/txt
  - Генерация промежуточных форматов для LISP (упрощённый CSV)
  - Batch-обработка множества файлов
  - Будущее: GUI через Tk/PyQt

- **.NET** — на будущее, если потребуется (например, плагин-палитра в Civil 3D
  с GUI или интеграция, недоступная через LISP). До явной потребности — не вводим.

## Альтернативы

1. **Только AutoLISP** — отвергнуто. Парсинг Excel и batch-обработка вне CAD
   — это уже не его сильная сторона; код становится хрупким.
2. **Только .NET / ObjectARX** — отвергнуто на старте. Высокий порог входа
   (Visual Studio, компиляция), медленная итерация для прототипов, избыточно
   для большинства задач Шамиля.
3. **VBA** — отвергнуто. Autodesk объявил его deprecated, поддержка
   ограничена.
4. **Standalone Windows-приложение через COM** — отвергнуто на старте.
   Сложнее, медленнее, дороже. Можно вернуться, если появится требование
   управлять CAD из внешнего UI.

## Последствия

**Положительные**:
- Быстрый MVP на LISP без новых зависимостей
- Подготовка данных в Python — стандартный, легко тестируемый код
- Развязка ответственности: LISP знает CAD, Python знает данные
- Лёгкая замена/расширение: новый формат входа = новый Python-парсер,
  LISP не трогаем

**Отрицательные / риски**:
- Две технологии = две точки знаний; нужны мини-конвенции для каждой
- Передача данных LISP↔Python через файлы (CSV/JSON) — простая, но
  не realtime; для текущих задач достаточно
- Нужен Python на машине Шамиля (одноразовая настройка)

**Отзывность**: средняя. На LISP мы будем сильно завязаны (это окупается),
от Python к .NET перейти можно, но миграция кода нетривиальная.

## Критерии пересмотра

Пересмотреть, если:
- Появится требование к интерактивному GUI внутри Civil 3D, не покрываемое LISP
- Производительность LISP станет узким местом (> сотен тысяч точек регулярно)
- Появится потребность в standalone-приложении, управляющем CAD извне
