# Workflow — как работаем над проектом

Этот документ описывает рабочий процесс. Конституция (`CLAUDE.md`) задаёт правила,
этот файл — рутину.

---

## Spec-Driven Development (SDD) — общая схема

```
Идея от Шамиля
    ↓
Уточнение через AskUserQuestion (если нужно)
    ↓
Спека в specs/NNN-feature.md
    ↓
[если архитектурно] ADR в docs/decisions/
    ↓
Реализация в src/
    ↓
Проверка на samples/
    ↓
Обновление status/PROGRESS.md, status/HANDOFF.md
    ↓
Commit
```

**Ничего не пропускаем.** Тривиальные правки (≤5 строк, без изменения поведения) —
исключение, остальное идёт по циклу.

---

## Жизненный цикл задачи

### 1. Старт сессии

- Прочитать `CLAUDE.md`
- Прочитать `status/HANDOFF.md`
- Прочитать `status/ROADMAP.md`
- Если работаем над фичей — её спеку
- Вывести Шамилю: *"Прочитал CLAUDE.md, понял правила. Иду в HANDOFF.md."*

### 2. Definition of Ready (DoR)

Перед кодом проверить:
- [ ] Спека написана и понятна
- [ ] Источник данных известен
- [ ] Критерий приёмки сформулирован

Если хоть что-то не выполнено — `AskUserQuestion`.

### 3. Реализация

- Читай реальные `samples/` ДО написания кода (R5)
- Код пишется строго по спеке
- TODO-list ведётся через `TodoWrite`, обновление в реальном времени
- Не батчить пометку "completed" — отмечать сразу

### 4. Проверка

- Прогон на реальных данных из `samples/`
- Если автоматический прогон невозможен (например, нужен Civil 3D) —
  явно записать "не проверено, требуется ручной запуск"
- Edge-cases — обработать или зафиксировать в `status/ISSUES.md`

### 5. Definition of Done (DoD)

См. `CLAUDE.md` §4. Каждый пункт — явный ответ.

### 6. Документирование

- `status/PROGRESS.md` — что добавилось (одна строка)
- `status/HANDOFF.md` — обновить блок "На чём остановились" / "Следующий шаг"
- `status/QUALITY.md` — обновить метрики, если применимо
- ADR — если решение архитектурное

### 7. Commit

Перед коммитом — самопроверка DoD в чате (обязательный ритуал):

```
Самопроверка DoD:
- Спека: ✅
- Код по спеке: ✅
- Тест на samples: ✅ (или "не проверено — причина")
- Edge-cases: ✅ (или ссылка на ISSUE)
- HANDOFF: ✅
- PROGRESS: ✅
- ADR: не применимо
```

Без честного чеклиста — коммит запрещён.

### 8. Конец сессии

`status/HANDOFF.md` должен позволить **любой нейросети** поднять проект с
полу-слова. Это главный артефакт сессии.

## Когда писать ADR

Решение требует ADR, если оно:
- Определяет технологию (LISP vs .NET)
- Определяет интерфейс (как именно команды называются)
- Создаёт ограничение на будущее (формат файлов, протокол)
- Может потребовать пересмотра позже

Решение **НЕ требует** ADR, если оно:
- Локальное (имя переменной)
- Очевидно вытекает из существующего ADR
- Тривиально

---

## Когда эскалировать через AskUserQuestion

- Спека противоречит сама себе или реальным данным
- Появилась развилка с долгосрочными последствиями
- Хочешь сократить scope (R1!)
- Не нашёл данных в `samples/`, нужны от Шамиля
- Нашёл способ сильно лучше, чем в спеке

**Не используй догадки.** Лень спросить = нарушение R1.

---

## Анти-лень: ритуал самопроверки

Перед "готово" задай себе пять вопросов:

1. Я **прочитал** реальные данные или выдумал структуру?
2. Я **проверил** код или предполагаю, что он работает?
3. Я **реализовал всё** из спеки или подмножество?
4. Я **обновил** HANDOFF и PROGRESS или коммичу молча?
5. Если меня спросят "почему именно так" — у меня есть ADR/спека?

Один "нет" — задача не готова.
