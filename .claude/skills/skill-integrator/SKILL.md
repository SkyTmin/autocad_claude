name: skill-integrator
description: Meta-skill that integrates other Claude skills into a project's existing file structure. Prevents duplicate files, parallel configurations, and orphan artifacts when running or installing skills like /init, /fewer-permission-prompts, /security-review, /review, /simplify, /update-config, /session-start-hook. Use BEFORE running any skill that writes files. Also use when ADDING a new skill to the project — it analyzes the new skill's SKILL.md, rewrites paths to match project conventions, and registers it in the project's integration map. Reads project-specific rules from `.claude/skills/skill-integrator/integration-map.md`.

# skill-integrator

Универсальный мета-скилл, который встраивает другие Claude-скиллы в существующую файловую структуру проекта. Предотвращает дубликаты, параллельные конфиги и осиротевшие артефакты.

> Marketplace-ready: фреймворк (этот файл) универсален. Конкретные правила
> проекта живут в соседнем `integration-map.md`. Чтобы адаптировать скилл
> под новый проект — скопируйте `integration-map.md.example` в
> `integration-map.md` и заполните карту.

---

## 1. Зачем

Claude-скиллы пишутся **без знания вашего проекта**. Они создают
"стандартные" файлы (`.claude/settings.json`, `README.md`, `notes.md`,
`decisions.md`) даже когда у вас уже есть аналог под другим именем.
Без вмешательства получается:

- `settings.json` рядом с `settings.local.json`
- `notes.md` рядом с `HANDOFF.md`
- `decisions.md` рядом с `docs/decisions/`

Два файла — одна цель. Путаница, дрейф, регрессии.

Этот скилл решает проблему **тремя способами**:

1. **Маршрутизация** — перед запуском чужого скилла перенаправляет его
   вывод в существующие файлы согласно карте.
2. **Адаптация** — при добавлении нового скилла в проект редактирует
   его `SKILL.md`, чтобы пути соответствовали проекту, **либо** добавляет
   правило-редирект в карту.
3. **Журнал прецедентов** — записывает каждое решение, чтобы будущие
   сессии не передоговаривались заново.

---

## 2. Установка в новый проект

1. Скопировать папку `.claude/skills/skill-integrator/` целиком в новый проект.
2. Скопировать `integration-map.md.example` → `integration-map.md`,
   заполнить под структуру нового проекта (минимум: где живут settings,
   статус, ADR, спеки, хуки, тесты, samples).
3. В корневой `CLAUDE.md` (или `AGENTS.md`) проекта добавить ссылку:
   > Перед запуском любого скилла, который пишет файлы — сначала
   > вызови `/skill-integrator` или прочитай
   > `.claude/skills/skill-integrator/integration-map.md`.
4. Закоммитить.

---

## 3. Три режима работы

### Режим A. Перед запуском чужого скилла (маршрутизация)

**Триггер**: пользователь говорит "запусти `/X`" или "сделай через `/X`".

**Алгоритм**:
1. Прочитать `integration-map.md` (раздел «Карта путей» и «Известные скиллы»).
2. Прочитать описание целевого скилла `/X` (`name`, `description`,
   тело SKILL.md). Извлечь все файлы/пути, которые он собирается
   создать или модифицировать.
3. Для каждого пути найти редирект в карте.
   - Если редирект есть → запомнить.
   - Если нет → §6 «Неизвестный случай».
4. Запустить `/X`. После каждой записи файла **проверять**: попал ли
   он по правильному адресу? Если скилл создал файл по дефолтному
   пути — слить в правильное место и удалить дубликат.
5. Записать строку в журнал прецедентов карты.
6. Сообщить пользователю: что было запущено, что куда легло, какие
   дубликаты были предотвращены.

### Режим B. Добавление нового скилла в проект (адаптация)

**Триггер**: пользователь говорит "добавь скилл `<X>` в проект",
"установи скилл из `<url>`", "интегрируй этот скилл".

**Алгоритм**:
1. Получить `SKILL.md` нового скилла (из URL, локального файла,
   маркетплейса).
2. **Прочитать его полностью**. Извлечь:
   - Все упоминания путей (`.claude/...`, `docs/...`, `<root>/...`).
   - Все упоминания типов артефактов (settings, hooks, ADR, specs,
     status, tests, samples, hooks).
   - Команды записи (Write, Edit, mkdir).
3. Сравнить с `integration-map.md`. Для каждого совпадения:
   a. **Если SKILL.md нового скилла можно редактировать** (это копия
      в нашем репо, не маркетплейсный апдейт-канал) →
      **редактировать SKILL.md на месте**, заменив дефолтный путь
      на путь из карты. Это предпочтительный путь.
   b. **Если SKILL.md нельзя редактировать** (например, marketplace-скилл
      с авто-обновлениями) → добавить запись в раздел «Известные
      скиллы» карты с правилом маршрутизации.
4. Если у нового скилла есть категории, которых **нет** в карте —
   §6 «Неизвестный случай».
5. Зарегистрировать новый скилл в карте: добавить в раздел
   «Известные скиллы» с описанием его поведения после интеграции.
6. Записать в журнал прецедентов: какие правки были внесены и почему.
7. Закоммитить новый скилл и обновлённую карту **одним коммитом**,
   чтобы они никогда не расходились.

### Режим C. Аудит установленных скиллов

**Триггер**: "проверь все скиллы", "audit skills", "/skill-integrator audit".

**Алгоритм**:
1. Перечислить все скиллы в `~/.claude/skills/` и `.claude/skills/`.
2. Для каждого извлечь пути из SKILL.md.
3. Сверить с картой. Найти:
   - Конфликты: скилл пишет туда, где у проекта своё правило.
   - Сироты: скилл пишет в места, не упомянутые в карте.
4. Выдать отчёт: список скиллов, их статус (✅ ок / ⚠ конфликт /
   ❓ не покрыт картой), рекомендуемое действие.

## 4. Жёсткие инварианты (универсальные)

Эти правила действуют **в любом проекте**, независимо от карты:

- **И-1: Один файл = одна цель.** Никаких параллельных файлов с
  пересекающейся ответственностью.
- **И-2: Расширяй, не плоди.** Новая категория сведений → сначала
  вопрос пользователю → строка в карте → только потом файл.
- **И-3: Карта — авторитет.** Дефолтные пути скиллов проигрывают
  записям в карте.
- **И-4: Журнал прецедентов append-only.** Прошлые решения
  не переписываются молча. Изменилось решение — новая строка,
  старая помечена как `superseded`.
- **И-5: Скилл и карта коммитятся вместе.** При добавлении нового
  скилла его файлы и обновление карты должны быть в одном коммите —
  иначе они разойдутся.

## 5. Структура файлов скилла

```
.claude/skills/skill-integrator/
├── SKILL.md                     ⭐ этот файл — фреймворк
├── integration-map.md           ⭐ данные конкретного проекта
└── integration-map.md.example   шаблон для нового проекта
```

`integration-map.md` структурно содержит:
- **§1 Карта путей** — таблица «дефолт скилла → реальное место в проекте»
- **§2 Известные скиллы** — преднастроенные интеграции для частых скиллов
- **§3 Жёсткие правила проекта** — что нельзя трогать (Конституция, ключи и т.п.)
- **§4 Журнал прецедентов** — история интеграций, append-only

---

## 6. Если случай не покрыт картой

**Не угадывай.** Всегда `AskUserQuestion`:

> "Скилл `/X` хочет создать `<path>` для `<purpose>`. В карте интеграции
> такого правила нет. Куда положить — `<option-1>` или `<option-2>`?
> После твоего ответа я добавлю правило в карту."

После ответа — **обязательно**:
1. Добавить строку в `integration-map.md` §1 или §2.
2. Записать решение в §4 (журнал прецедентов) с датой и причиной.
3. Закоммитить отдельно от запуска скилла, чтобы был чистый diff.

## 7. Шаблон сообщения пользователю после работы

После завершения любого режима — короткий отчёт:

```
✅ Скилл /X запущен / интегрирован.

Что куда легло:
  - <output-1>  →  <map-entry>
  - <output-2>  →  <map-entry>

Предотвращено дубликатов: N
Новых правил в карте: M
Журнал прецедентов: запись от <date>, коммит <sha>
```

## 8. Расширение фреймворка (контрибьютинг в маркетплейс)

Этот файл — **универсальный фреймворк**. Не вносите сюда
проектно-специфичные данные. Вместо этого:

- Новые категории артефактов → шаблон `integration-map.md.example`
- Новые режимы работы → новый раздел §3.X в этом файле
- Новые инварианты, которые универсальны для всех проектов → §4

При публикации в маркетплейс убедитесь, что:
- В `SKILL.md` нет упоминаний конкретных проектов
- `integration-map.md` **не публикуется** (он персональный)
- `integration-map.md.example` содержит **только пустой шаблон с комментариями**

## 9. Метаданные

  структур при работе со скиллами Claude Code.

- **Зависимости**: нет.
- **Лицензия**: укажите при публикации.
